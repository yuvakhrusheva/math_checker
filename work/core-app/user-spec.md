# User Spec: core-app

## Что делаем

Streamlit-приложение для автоматической проверки рукописных математических работ учеников 2–3 классов Азербайджана. Оператор добавляет когорты (папки с PDF-сканами на Google Drive), приложение обрабатывает их в фоне через vision LLM, выставляет баллы по готовым критериям и экспортирует результаты в Excel.

## Зачем

Ручная проверка ~1200 работ занимает много времени и даёт непоследовательные результаты. Приложение автоматизирует распознавание и выставление баллов, оставляя оператору только контроль качества для спорных случаев.

## Как должно работать

### Сценарий 1: Первоначальная настройка

1. Оператор запускает приложение (`streamlit run app.py`)
2. На экране «Criteria Management» оператор загружает JSON-файлы с критериями (по одному для каждой комбинации: класс × язык × вариант)
3. Приложение валидирует JSON и сохраняет в `criteria/`

### Сценарий 2: Добавление когорты

1. На главном экране оператор нажимает «Add Cohort»
2. Заполняет форму: ссылка на папку Google Drive, школа, класс (номер + буква), ФИО учителя, дата тестирования, язык (ru/az)
3. Приложение проверяет, что для заданного класса+языка есть файлы критериев. Если нет — показывает ошибку, когорта не добавляется
4. Когорта добавляется в очередь со статусом **Pending**
5. Оператор может сразу добавлять следующие когорты, не дожидаясь обработки

### Сценарий 3: Обработка

1. Оператор нажимает кнопку **«Start Processing»** на главном экране — запускается последовательная обработка всех когорт в очереди со статусом Pending
2. Для каждой когорты: скачивает PDF-файлы с Google Drive, конвертирует каждую страницу в изображение, отправляет в vision LLM с инструкцией и критериями
3. LLM возвращает JSON: для каждого задания — `recognized_answer`, `score`, `max_score`, `confidence: low|high`
4. Если `confidence: low` для любого ответа — студент помечается как «требует проверки»
5. Если PDF полностью нечитаем — студент получает статус `unreadable`, в список ошибок, в Excel не включается
6. Если вариант теста не распознан — студент идёт на ручную проверку с возможностью оператора указать вариант вручную
7. Успешно обработанные результаты сохраняются в SQLite. Уже обработанные студенты пропускаются при повторном запуске
8. Прогресс отображается на главном экране (прогресс-бар + статус когорты)

### Сценарий 4: Ручная проверка (Review)

1. После завершения когорты оператор видит уведомление на главном экране
2. Нажимает «Review» — открывается панель с перечнем студентов, требующих проверки
3. Для каждого студента: скан страницы, содержащей задание с `confidence: low`, с указанием номера задания; и поле для редактирования ответа
4. Оператор исправляет ответ → балл пересчитывается автоматически согласно критериям
5. Для студентов с нераспознанным вариантом — выпадающий список для выбора варианта

### Сценарий 5: Экспорт

1. Кнопка «Export to Excel» доступна всегда
2. Создаётся файл `results_YYYY-MM-DD_HH-MM.xlsx` с двумя листами:
   - **Answers**: школа, класс, учитель, дата, student_id, имя (справочно), ответ по каждому из 16 заданий
   - **Scores**: школа, класс, учитель, дата, student_id, балл по каждому заданию, итоговый балл, уровень успеваемости
3. Студенты с незавершённой проверкой отмечаются `PENDING` в соответствующих колонках
4. Строки отсортированы: школа → класс → student_id

## Ограничения

- Запускается локально на машине оператора, веб-деплой не предусмотрен
- Количество страниц в PDF не фиксировано (финальная типографская версия бланков ещё не готова) — обработчик должен поддерживать любое количество страниц
- Имя студента распознаётся из рукописного текста — ненадёжно, используется только как справочная информация; основной идентификатор — `student_id`
- Критерии для Grade 2 RU и Grade 3 RU уже существуют и будут загружены до начала работы. AZ-критерии пока отсутствуют — AZ-когорты не могут быть добавлены до их загрузки через Criteria Management
- Уровни успеваемости для 2-го класса не определены — колонка уровня в Excel для grade 2 остаётся пустой (TBD)
- Интерфейс на английском языке

## Риски

- **Ненадёжное распознавание рукописного варианта теста:** LLM может не распознать номер варианта с бланка. **Митигация:** студент автоматически попадает в Review Panel с возможностью указать вариант вручную.
- **Высокий процент неуверенных случаев:** если LLM часто возвращает `confidence: low`, объём ручной работы может быть сопоставим с ручной проверкой. **Митигация:** после MVP — тестовый прогон на прошлогодних данных; если процент высок — настройка промпта или порога уверенности.
- **Стоимость LLM-вызовов:** при 1200 студентах и нескольких страницах на PDF стоимость может вырасти. **Митигация:** LiteLLM позволяет переключаться на более дешёвую модель в `config/settings.json`; resumable processing исключает повторные вызовы.
- **Неизвестное количество страниц:** финальный бланк ещё не вёрстан. **Митигация:** обработчик итерирует по всем страницам PDF без предположений о их количестве.

## Технические решения

- Все LLM-вызовы идут через **LiteLLM** — смена провайдера одной строкой в `config/settings.json`.
- Аутентификация Google Drive — через **service account** (`GOOGLE_SERVICE_ACCOUNT_JSON` в `.env`); пользователь OAuth не используется.
- Вариант теста (1 или 2) **распознаётся автоматически** из скана бланка — оператор не вводит его вручную.
- Обработка когорт **последовательная** (не параллельная): упрощает реализацию на Streamlit, достаточно для объёма ~1200 студентов.
- Обработка **resumable**: перед обработкой каждого студента проверяется статус в SQLite; уже обработанные пропускаются.
- **Уникальный ключ студента** — автоинкрементный `student_id`; имя из рукописного текста хранится справочно.
- Добавление когорты **блокируется**, если для её комбинации класс+язык отсутствует файл критериев — ошибка на этапе формы.
- Студент со **полностью нечитаемым PDF** исключается из Excel и когорты; попадает в отдельный список ошибок с пометкой «unreadable — requires rescanning».
- **Экспорт доступен всегда**; нерешённые студенты отмечаются `PENDING` в Excel.
- **Критерии загружаются через UI** в `criteria/` — не нужно вручную копировать файлы.

## Тестирование

**Unit-тесты:** делаются всегда, не обсуждаются.

**Интеграционные тесты:** делаем — реальный тестовый Google Drive аккаунт + тестовая папка с PDF-сканами. Drive API и LLM-вызовы не мокаются; используется отдельный тестовый аккаунт.

**E2E тесты:** не делаем на этапе MVP — заменяются ручным прогоном на прошлогодних данных (≤3% расхождение с эталонной проверкой).

## Как проверить

### Агент проверяет

| Шаг | Инструмент | Ожидаемый результат |
|-----|-----------|-------------------|
| 1. Загрузить валидный criteria JSON через UI | Playwright / Streamlit test | Файл появляется в `criteria/`, статус «loaded» |
| 2. Попробовать добавить когорту без критериев | Playwright / Streamlit test | Форма показывает ошибку, когорта не добавляется |
| 3. Запустить обработку тестовой папки Drive (5 PDF) | pytest integration | Все 5 студентов в SQLite со статусом processed/review/error |
| 4. Вызвать grader с fixture LLM-ответом (confidence: low) | pytest unit | Студент помечен как requires_review |
| 5. Вызвать grader с пустым ответом | pytest unit | score = 0 |
| 6. Экспортировать Excel | pytest unit | Файл создан, 2 листа, правильные заголовки, student_id проставлены |
| 7. Повторный запуск обработки | pytest integration | Уже обработанные студенты пропущены (нет повторных LLM-вызовов) |

### Пользователь проверяет

- **Тестовый прогон на прошлогодних данных:** запустить полный цикл на известном наборе работ, сравнить баллы в Excel с эталонной ручной проверкой. Расхождение должно быть ≤3%.
- **Review Panel:** открыть панель проверки, убедиться что скан страницы отображается с указанием номера задания, исправление ответа пересчитывает балл.
- **Восстановление состояния:** закрыть браузер, открыть снова — все когорты и результаты на месте.
